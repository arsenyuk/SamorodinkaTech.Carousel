# AGENTS.md

Руководство для AI-ассистентов, работающих с репозиторием SamorodinkaTech.Carousel.

Правила адаптированы из SamorodinkaTech.Fiducia (дисциплина ассистента, вызов инструментов, логирование и аудит) с учётом специфики Carousel.

---

## Канарейка — обращение «Успешнейший»

- **Каждое** ответное сообщение пользователю начинается с **«Успешнейший!»** (или «Дважды Успешнейший!» для чатов агентов).
- Без исключений. Без «иногда». Без «когда уместно».
- Сообщения в чатах агентов начинать с **«Дважды Успешнейший!»**.

## Общие правила поведения (КРИТИЧНО)

### Приоритет основной задачи

Основной запрос пользователя выполняется первым и до конца. Любые сопутствующие мета-правки (документация, правила, рефакторинг «по пути») — только после завершения основной задачи и не должны её подменять.

### Сначала ответ на вопрос, потом действие

Если пользователь задал явный вопрос — сначала содержательный ответ в тексте, только после этого (или вместе с этим) — правки файлов. Молча переходить к правкам, игнорируя заданный вопрос, запрещено.

### Язык проекта

Во всех артефактах проекта (код, документация, коммиты, UI) — **только русский и английский**. Другие языки запрещены без явного согласования. При обнаружении — немедленно заменять.

### Последовательное исполнение (КРИТИЧНО)

- Задачи выполняются **строго последовательно**: шаг за шагом, без пропусков и без параллельного выполнения нескольких шагов.
- Каждый шаг проверяется перед переходом к следующему (сборка, тест, валидация).
- **Запрещено**: читать файлы по кругу без внесения изменений; дублировать одно и то же чтение N раз; выполнять неподтверждённые изменения.
- Перед началом — прочитать план; по выполнении каждого шага — проверить результат; при ошибке — **немедленно исправить** и перепроверить.

### Уточнение затрагиваемых модулей перед реализацией (scope creep)

Перед реализацией задачи, затрагивающей более одного модуля, явно уточнить полный список затрагиваемых модулей. Реализация ограничивается ровно тем скоупом, который запросил пользователь. Дополнительные изменения — только по явному запросу.

### Изменение только затронутых файлов сессии (КРИТИЧНО)

При обнаружении проблемы разрешается изменять **только файлы, затронутые в рамках текущей сессии**. Для сканирования или изменения других файлов — **спросить пользователя**. Исключение: автоматические кросс-ссылки между уже изменёнными файлами.

### Диагностика сложной логики перед модификацией (КРИТИЧНО)

- Перед модификацией метода со сложной логикой (3+ уровня вложенности, перекрёстные вызовы) прочитать **все** связанные методы (вверх и вниз по стеку) и построить граф зависимостей. Если граф неполон — **спросить пользователя**.
- Запрещено переписывать метод «с нуля», если достаточно минимальной правки.
- Изменение отлаженного production-метода требует **явного подтверждения пользователя**.

### Автономность исполнения

Остановка исполнения допустима только при наличии реального вопроса к ассистенту, необходимости уточнить неоднозначную трактовку, риске непоправимого действия или недостающих данных, которые невозможно получить самостоятельно. Диагностика (чтение файлов, `git status`, `grep`) — часть выполнения задачи, а не повод для промежуточной остановки с отчётом.

### Приём результата инструмента

Результат инструмента принимается на веру только после повторной проверки (перечитать файл, `dotnet build`, тесты). Плейсхолдеры и «я это уже сделал» без проверки запрещены.

### DRY

Перед копированием кода проверять, есть ли уже сервис/хелпер для этой задачи. Дублирование — ошибка, которую нужно исправлять немедленно.

### Консолидация библиотек (КРИТИЧНО)

Всегда следить за согласованностью версий NuGet-пакетов: версии задавать только в `Directory.Packages.props`, не дублировать в `.csproj`. При добавлении/обновлении пакета проверять конфликты версий (MSB3277 и т.п.) и выравнивать их; расхождения версий одного пакета между проектами — немедленно чинить.

### Миграции EF только по команде (КРИТИЧНО)

- `dotnet ef migrations add` / `database update` — **только по явной команде пользователя**; без команды не выполнять ни создание, ни применение миграций.
- `AutoMigrate` в Production — **всегда false**. Включение в проде — только по команде пользователя («я скажу, когда включить миграции»).
- Деплой, содержащий новые миграции, — не выполнять, пока пользователь не разрешил.

### Всё остальное — в этом файле

Все операционные правила — **исключительно в `AGENTS.md`**. `MEMORY.md` — кросс-сессионные знания, не операционные правила. При противоречии — `AGENTS.md` имеет приоритет. При обнаружении нового правила — добавлять сюда.

### Краткость и простой язык

Правила — **кратко и конкретно** (1–3 предложения). Запрещено включать длинные описания инцидентов, примеры кода на 20+ строк, предысторию. Маркировка `(КРИТИЧНО)` — для нарушений, критичных для проекта.

Общение — **простым понятным языком**: без канцелярита, лишнего жаргона и раздувания формулировок. Одна мысль — одно предложение. Если можно сказать короче и яснее — говорить короче и яснее.

## Правила вызова агентов и инструментов (КРИТИЧНО)

### Дисциплина вызова инструментов

- Каждый вызов инструмента — настоящий вызов с реальными аргументами, а не текстовый пример.
- Плейсхолдеры (`...`, `TODO`, `REPLACED_PLACEHOLDER` и т.п.) внутри аргументов реального вызова запрещены.
- После каждого вызова, изменяющего файл, результат немедленно проверяется повторным чтением файла в том же ответе, прежде чем сообщать об успехе.
- Если проверка показала, что изменение не применилось — попытка немедленно повторяется с точным содержимым, без переспрашивания пользователя.

### Дисциплина долгих команд и диагностики

- Долгие операции (сборка docker, pull, npm install, dotnet publish) — только с явным большим `timeout` либо в фоне с лог-файлом; полный вывод сохранять в файл, не заворачивать в `tail`. (КРИТИЧНО)
- zsh: слово с `=` в начале и glob без совпадений роняют всю команду; для удалений сначала вывести список, потом удалять по нему. (КРИТИЧНО)
- `$?` после пайпа — код последней команды; проверять результат через `if grep -q` или `set -o pipefail`.
- Прежде чем сказать «не работает» — убедиться, что проверка бьёт в реальность (CWD процесса, каталог логов, версия конфига в bin/образа); доступ через localhost в контейнере (`trust` в pg_hba) не доказывает работоспособность пароля. (КРИТИЧНО)
- Форматы/подписи/запросы генерировать только после чтения валидатора или реализации; `Read` — `offset` с первого вызова; `Edit` — old ≠ new.
- Субагент: максимум 2 попытки, затем честный отказ и альтернатива.

### Git: коммит, push, подтверждения (КРИТИЧНО)

- Коммит по команде пользователя включает отправку в `origin`; после переписывания истории — сразу `git push --force`. Финальное состояние задачи обязано быть на remote.
- Спрашивать/ждать подтверждение разрешено только если это прямо требует AGENTS.md или утверждённый план — иначе выполнять, не останавливаясь на вопросе.

### Запрещено придумывать пути (КРИТИЧНО)

- Запрещено **придумывать**, **догадываться** или **реконструировать по памяти** пути к файлам, классам, проектам.
- Перед обращением к файлу/проекту — **сначала** найти через glob/grep, потом работать с найденным путём.
- Запрещены конструкции вида `src/.../SomeService.cs`, если путь не получен из glob/grep/read в этой же сессии.
- Если путь не удаётся найти — **спросить пользователя**, а не предлагать наиболее вероятный путь.
- При ошибке Edit `File not found` — **немедленно** Glob-ом найти реальный путь и повторить по нему. Не повторять Edit с другим «вероятным» путём.
- При ошибке Edit `String not found` — перечитать файл, найти точное вхождение, повторить с точным текстом.

### Только инструменты из surface (КРИТИЧНО)

- Использовать **только** встроенные инструменты: Glob, Grep, Read, Edit, Write, Bash.
- Запрещено вызывать внешние CLI-утилиты через Bash, если они не входят в стандартный набор ОС: `rg`, `fd`, `fzf` и т.п. — **не существуют** в этом окружении.
- Для поиска файлов — Glob. Для поиска по содержимому — Grep. Для чтения — Read. Для правки — Edit/Write.
- `find`, `ls`, `cat` через Bash — только когда Glob/Grep/Read не покрывают задачу (например, `find` с `-path` для исключения bin/obj).

### Экранирование кавычек в shell (zsh)

- Аргумент `command` без оборачивания всей команды в дополнительные внешние кавычки — только те, которые нужны самой shell-команде.
- Многострочные сообщения коммита — через несколько флагов `-m "строка1" -m "строка2"`, не `\n` внутри одной строки.
- `no such file or directory` / `command not found` — почти всегда сигнал об ошибке экранирования; упростить кавычки, а не менять путь.

### Видимость агентов / vision-моделей

- Если субагент или vision-инструмент упал с ошибкой аутентификации/недоступности — **не повторять** вызов в цикле. Описать проблему пользователю и предложить альтернативу.
- Параллельные агенты — только для независимых задач; последовательная цепочка зависимых шагов — только последовательно.

### Остановка только с реальным вопросом

Не останавливаться с отчётом «прочитал X, теперь спрошу» на каждую мелочь. Вопрос пользователю — только при реальной неоднозначности, риске или отсутствии данных.

## Политика логирования ошибок и аудита (КРИТИЧНО)

### Разделение: аудит-лог vs лог приложения

| Куда | Что логируется | Пример |
|------|----------------|--------|
| **Аудит-лог** | Контроль доступа: разрешён/запрещён, вход/выход, попытки нарушения | `ACCESS_DENIED: ...` |
| **Лог приложения** (`ILogger`) | Бизнес-операции: CRUD, импорт, вычисления | `Добавлена публикация: ...` |

- Успешные операции CRUD пишутся в **лог приложения**, не в аудит.
- Аудит — **только** для контроля доступа и security-событий.
- Запрещено писать бизнес-операции в аудит-лог и наоборот.

### Все ошибки валидации логируются перед возвратом (КРИТИЧНО)

Каждый `Results.BadRequest(...)` / возврат ошибки валидации **обязан** сопровождаться `logger.LogWarning(...)` с описанием и ключевыми параметрами (Id, статус и т.д.). Исключение: ошибки в `catch`, где `LogWarning(ex, ...)` уже вызывается.

Причина: без логирования пользователь видит ошибку в UI, но в логе нет записи.

### Обработка ошибок (КРИТИЧНО)

- Пустые `catch { }` / `catch { /* ignore */ }` **запрещены** — подавление без логирования скрывает причину.
- Каждый `catch` как минимум логирует исключение:
  ```csharp
  catch (Exception ex)
  {
      _logger.LogWarning(ex, "Описание контекста ошибки");
  }
  ```
- Намеренное игнорирование — только с явным комментарием-обоснованием.
- При показе/логировании ошибок БД — извлекать **самое глубокое** сообщение из `InnerException` (EF оборачивает реальную ошибку). Использовать unwrap, не голый `ex.Message` наружу без контекста.

### Не подменять ошибки внешних сервисов (КРИТИЧНО)

- При показе ошибки внешнего сервиса — **реальный** `ex.Message` (или краткий контекст + `ex.Message`), а не выдуманная интерпретация.
- Исключение логировать целиком: `LogWarning(ex, ...)`.
- Запрещено: «требуется расширенный тариф X» — это догадка, а не факт.

### Логирование URL при ошибках HTTP (КРИТИЧНО)

При ошибке HTTP-запроса (4xx/5xx, исключение) в лог **обязательно** — полный URL, метод, код ответа и тело/исключение:
```csharp
Logger.LogWarning(ex, "Ошибка HTTP {Method} {Url}", method, requestUrl);
```

### Логирование отказов в доступе (КРИТИЧНО)

Каждый отказ в доступе (403, Forbidden) **обязан** записываться в лог с логином/идентификатором пользователя, ролями и целевым ресурсом:
`ACCESS_DENIED: пользователь {Login} (роли: {Roles}) попытался обратиться к {Resource}`

### Лог аудита — только бизнес-события безопасности

В аудит-лог попадают **только**: вход/выход, изменение данных доступа, обращение к внешним системам security-контекста, ошибки доступа. Служебные HTTP-запросы (роутинг, health-check, загрузка статики) — **не логируются** в аудит.

### Обязательные поля записи аудита (КРИТИЧНО)

Запись аудита **обязана** содержать:
- `actionCode` — иерархический код (`ГРУППА:Подгруппа:Действие`), например `AUTH:LOGIN_SUCCESS`, `AUTH:LOGIN_FAILED`, `AUTH:LOGOUT`, `ACCESS:PAGE_DENIED`, `ACCESS:API_DENIED`, `EXTERNAL:{Service}:{Action}`
- `userId` — обязателен, кроме анонимного входа; `null` — ошибка, которую надо чинить
- `login` — логин (или `anonymous`), **не ФИО**; минимальная идентификация
- `userIp` — IP клиента (`"unknown"`, если не определён)

Запрещены общие неиерархические коды типа `PAGE_ACCESS`.

### Формат записи аудита

- `description` — **читаемый текст** без Unicode-escape и JSON: `{Действие} {Объект} {Идентификатор} — {Результат}`
- Запрещено: JSON-структуры, escape-последовательности, технический шум в описании.

### Аудит внешних интеграций — с IP клиента

Декораторы/клиенты внешних интеграций **обязаны** передавать реальный IP клиента, а не `"internal"`.

### Конфигурация логирования (КРИТИЧНО)

- Уровни, пути, форматы, sink'и, ротация — **только** в конфигурации (`appsettings.json` / переменные окружения), не в БД и не через UI.
- Изменение параметров логирования через UI — только по явному запросу пользователя.
- Чтение — через `IOptions<T>` / `IConfiguration`, без админ-экранов для путей логов.

### Чувствительные данные (КРИТИЧНО)

Ключи, пароли, токены, секреты — **не** в git-трекаемых файлах. Только `.env` / переменные окружения. В `appsettings` — пустые значения и `Enabled: false` для интеграций.

### Формат имён лог-файлов (ориентир)

- Приложение: `app-{yyyyMMddHH}.log` (Hourly)
- Аудит: `audit-{yyyyMMddHH}.log` (Hourly)
- Тестовые: `{type}-test-{yyyyMMdd}.log` (Daily)

В Carousel при необходимости Serilog-файлового sink'а — следовать `logs/carousel-api-.log` из текущего решения проекта; новые sink'и — только в конфигурации.
